Batch operations and export

The apply panel: A

A opens the apply panel: pick a scope (Rejects, Picks, Unrated, All but rejects — the survivors of a cull, everything you didn't throw out — or All), an action, and run it. Every action treats RAW + JPEG + sidecar as one unit — a moved photo takes its ratings with it.

With a selection built, the scope menu leads with Selected (N) — the live count of exactly the photos you hand-picked, whatever the current filter shows (a caption notes any that are filtered out of view). The scope never switches itself: pick it deliberately. If the selection empties while the scope still points at it, the panel reads Selected (0) and the button waits — it never quietly falls back to a broader scope. After a copy, export or upload the selection stays put for the next action; trash and move clear it with the photos.

The actions adapt to the active source:

  • Local folders: Copy to folder, Move to folder, Delete to trash (arm/confirm — the button asks for a second click), Export as JPEG, and Upload to Immich when a server is configured.
  • Immich sources: Download to folder (each photo lands with a sidecar carrying your edits), Archive on server, and Delete to trash on the server (same two-click confirm).

Upload to Immich sends RAW+JPEG pairs (stacked on the server with the JPEG as the stack cover, sidecar included so ratings import) and offers two destinations: a Server — with one Immich server configured it's pre-selected and inert; with several, the upload waits until you pick one (there is deliberately no silent default, and the completion summary names the server it went to) — and an Album. The album default, No album (timeline only), is plain upload; choosing an album adds every uploaded file to it, and the summary names it. Album choices are per-server: switching the Server resets the Album. If the album list can't be fetched, the panel says so (with a Retry button) instead of loading forever, and uploading to the timeline keeps working regardless.

Re-uploading is always safe — and since the checksum check landed, cheap: before any bytes move, culler asks the server which files it already holds (by content, not by name), and those are verified and skipped without re-sending anything. A re-run of a mostly-finished batch flies through in seconds, only actually transferring what's missing. While that check runs the counter reads Verifying instead of Uploading. When part of a pair was uploaded before — say the RAW is already up and sitting in a stack — the new upload joins that existing stack (newest JPEG in front) instead of creating a second one. Re-running a batch that already finished changes nothing.

One honest edge: if a photo's exact bytes already sit in the server's trash, the server reports it as a duplicate but leaves it trashed — uploading can't restore it, and culler can't either. That photo counts as uploaded with a warning naming the state; restore it in Immich's web UI to make it visible. It also never counts toward the trash-originals offer below — a copy in a trash that auto-empties is not a safe copy.

If the photos upload fine but the pair can't be stacked or the album add fails, that's reported as a warning on an uploaded photo, never as a failed upload. The common cause for the stack case is an API key minted before stacking shipped — add the stack.create permission to the key (or mint a fresh one) and re-run the upload: already-stored photos are verified and skipped, and only the stacks are created.

Before you click, the scope line shows what the batch weighs — "22 photos · 45 files · 1.18 GB". While it runs the panel shows a live "Uploading · N of M" count and a Cancel button; the bar under them fills by bytes, not photo count, so a batch of big RAWs can't paint itself half-done while most of the data is still queued. Under the bar, one line tracks what's left — "838 MB left · 3.1 MB/s" — and a small speed graph draws the transfer rate over the last two minutes in five-second bars. It has no warning colors on purpose: bars shrinking to the baseline IS what a stall looks like, and bars coming back is recovery. Cancel finishes the photo in flight, then stops — no half-uploaded pair — and the summary says what happened ("Cancelled — 12 of 37 uploaded"). A cancelled upload is safe to re-run; already-sent photos verify and skip. (Archive and server-trash are single server calls — nothing to count or cancel, they just show a spinner.)

Big files never look stalled: once a file has been on the wire for half a second, a second line appears under the batch readout with the file's name, its byte progress and the current speed — "DSC08551.ARW · 34.2 of 118.4 MB · 3.1 MB/s" — plus its own thin bar. When the last byte is sent the line says finishing… while the server checks the file in (normal, can take a few seconds); if bytes genuinely stop moving mid-transfer the line turns amber and says so plainly ("no movement for 8s") — a statement of fact, not a failure: a transfer that never recovers ends as that photo's error and the batch moves on. Cancelling mid-file adds "finishing, then stopping", because the current photo always completes. The same readout follows the batch into the corner pill's hover panel (which also carries the "MB left" line), and a single J upload to a server shows it too.

When a batch ends with failures, the summary names the photos — "20 photos uploaded to prd — 2 failed: DSC07717, DSC07803 (timed out waiting for a response)" — and hovering it shows the full technical error. The primary button becomes Retry 2 failed…: one click re-runs the batch, the stored photos verify and skip in moments, and only the failures actually re-send. A clean retry ends with every photo verified — "22 photos uploaded · 20 already stored" — and the trash-originals offer appears as if the batch had succeeded the first time. Changing any selector (photos, action, server, album) retires the Retry button; the plain Upload button does the same thing anyway, just without the count.

Uploading copies: your local files stay. When every photo in the batch is verified stored on the server — nothing failed, nothing cancelled — a second, separate offer appears under the summary: Trash N originals…. It is never automatic and never part of the upload itself. Click it once to arm, and it tells you exactly what will happen: originals go to the system Trash (recoverable there if you change your mind), and the server re-verifies every photo the moment you confirm — not at upload time, now. Click again to commit; a brief "Verifying" precedes the trashing, then the pair and its sidecar leave the folder together, with the same live progress and Cancel as any batch.

That last-second check is what makes the offer safe to trust. Before anything is trashed, culler asks the server — the one that actually took the uploads, even if you've browsed the server selector since — whether it still holds every photo's exact bytes, visible in its library. A photo whose server copy was deleted or moved to the server's trash in the meantime is kept on disk and the summary says so ("1 kept — no longer verified"): a copy in a trash that auto-empties is not a safe copy. And if the server can't be reached at all, nothing is trashed — "couldn't verify" never silently falls back to trusting the upload-time answer.

The offer is deliberately cautious. It only ever acts on the batch you just watched finish — close the panel, switch sources, or start anything else and it's gone (re-running the upload brings it back in seconds; already-stored photos are verified without storing anything twice). A photo whose file changed on disk between the upload and your click is skipped, never trashed. And if any upload failed, there is no offer at all — the Retry button is the path back to one.

Single export: J — and overwrite: Shift+J

J renders the current photo's edits (tone + crop) at full resolution through the same GPU pipeline that draws the screen — the file is pixel-identical to what you see — and writes a JPEG using the export preset (folder, filename suffix, quality, overwrite policy). For a photo with a RAW file, the export comes from a fresh full-resolution demosaic of the RAW (color, lens correction and your white balance included), exactly like the develop panel shows it; photos without a RAW export from the JPEG as before. Edit the folder, filename suffix and overwrite policy in the apply panel under Export as JPEG; everything persists between runs. The Quality slider sits in its own JPEG Quality card near the top of the same panel — visible on every source and under every action, because it governs every JPEG culler encodes: folder exports, Shift+J overwrites and J uploads to a server alike (the card says so in place). The default of 95 with full-resolution color (no chroma subsampling) lands in the same size and fidelity class as the camera's own JPEGs; raise or lower it once and it's remembered. Exports keep the camera's EXIF (MakerNotes intact), with orientation and pixel dimensions corrected for your crop.

Shift+J replaces the paired camera JPEG in place with the rendered edit — the one destructive file operation in the app. It asks for a second press and keeps the original as <name>.JPG.orig. If a .orig file already exists but is damaged or unreadable — a leftover from an interrupted run, or an unrelated file that happens to share the name — culler refuses the overwrite and tells you, rather than replacing your original with no good backup; remove that .orig and try again. What happens to your settings afterwards depends on what they were grading: a photo developed on its JPEG has its develop and crop reset — those edits are baked into the very pixels the sliders acted on, and left up they would apply twice. A RAW-paired photo keeps its develop sliders: they grade the RAW, which the overwrite never touches, so reopening the develop panel shows the exact grade that produced the new JPEG. The crop resets in both cases — the new JPEG is already cropped.

Edit uploads on a server source

On an Immich source, J downloads the original, renders your edit locally and uploads it — a RAW original, or the RAW behind a RAW+JPEG pair, gets the same full demosaic treatment as a local one: what the develop panel shows is what gets uploaded. The edit is always stacked with its original: a photo that wasn't in a stack founds a new one (edit on top, original behind it), and inside an existing stack the edit becomes the new stack cover — either way the server timeline shows your version fronting the original. Re-rendering the same photo replaces culler's previous version (it goes to the server trash) — the camera originals are never touched, and the stack never accumulates old renders. The new render also joins every album the photo belongs to, so albums keep showing the photo, fronted by the newest version. The photo in front of you follows immediately: the thumbnail and the full view swap to the uploaded render and the stack badge reflects the new grouping — no rescan needed. (Since the render already carries your grade, reopening develop shows it plainly while the RAW downloads, then switches to the live RAW rendition.) The upload renders at the JPEG Quality card's value — press A to see or change it, on a server source too, no batch action needed. The edit carries the original's metadata: camera, lens, exposure, GPS and the local capture time ride along even when the original is a format culler can't decode itself (an iPhone HEIC, say), so the server's Info panel reads the same on both. From an album view, the edit also joins that album. Only one export/upload runs at a time — a second J tells you one is already running and points at the pill.

A re-render bakes from the RAW, so it needs it: if the RAW can't be downloaded or decoded, the J stops with the cause in the status line and nothing is uploaded — culler never quietly re-uploads the previous version as if it were your new edit. Big originals get the same generous download time budget uploads have, so a slow connection means a longer wait, not a failure.

The pending-work pill

Anything running in the background shows in a small pill at the top-right: a batch with its live count ("Uploading · 12 of 37") right in the collapsed label, syncing ratings, a scan with its running total, an export by name, a stack loading, previews downloading. Hover it for the full list — and while a cancellable batch runs, its row in that list carries a ✕ that stops the batch after the current photo (the same cancel as the batch panel's button, for when the panel is closed). The pill exists to explain two things: why the app might feel slow right now (the wait is on the wire, not in the app), and why an action was just refused — a blocked keypress flashes the pill to point at the operation in its way. A failing sync shows here too, in amber, with the server's error; it keeps retrying on its own. When nothing is pending, the pill doesn't exist.
